# 高考志愿助手管理员权限与运营后台优化方案

日期：2026-06-29
范围：`/ai/gaokao` 高考志愿助手、App 内管理员入口、用户使用记录、生成权限重置、内部测试账号管理

## 1. 背景与目标

当前高考志愿助手已经有 App 用户登录、报告生成、报告删除和分享能力，但管理动作还分散在代码、环境变量和人工查库里：

- 离心之巅和练团长需要在 App 内直接进入管理员界面。
- 管理员需要查看哪些用户使用过项目。
- 管理员需要给用户重置志愿报告生成机会。
- 管理员需要给内部测试用户开启或取消无限生成。
- 后续运营需要知道谁生成了报告、谁删除了报告、哪些报告异常。

本方案目标不是做一个大而全后台，而是先做一个可靠的 App 内轻量管理台，把最常用、最容易出问题的运营动作收口。

## 3. 管理员身份定义

第一版管理员：

| 管理员 | App ID | 角色 |
| --- | --- | --- |
| 离心之巅 | `734275` | owner |
| 练团长 | `10` | admin |

第一版先不做复杂角色体系，只区分：

- 普通用户：只能生成、查看、删除自己的志愿报告。
- 管理员：可以进入管理台，查看用户列表，查看报告记录，重置用户生成机会，开关无限生成。

后续如果需要再扩展：

- owner：可添加/移除管理员。
- admin：可管理用户生成权限。
- viewer：只看数据，不允许重置。

## 4. 核心产品形态

### 4.1 App 内管理员入口

管理员打开 `/ai/gaokao` 时，在用户信息区域显示一个小的 `管理` 按钮。

建议位置：

- 在头像、昵称、报告状态附近。
- 不做夸张入口，不影响普通用户主流程。
- 普通用户完全看不到该按钮。

点击后进入：

```text
/ai/gaokao/admin
```

### 4.2 管理员首页

首页展示 4 个核心数字：

- 今日进入用户数
- 累计使用用户数
- 累计高考报告数
- 当前被设置为无限生成的用户数

第一版如果没有页面访问日志，今日进入用户数先用 `app_users.last_seen_at` 近 24 小时作为近似口径，并在文案里叫“近 24 小时进入过 AI H5 的用户”，不要伪装成精准高考页访问。

### 4.3 用户列表

列表字段：

- 昵称
- App ID
- 最后进入时间
- 用户状态
- 高考报告数
- 未删除报告数
- 已删除报告数
- 当前是否还能生成
- 是否无限生成
- 最近一次报告时间
- 其他模块生成记录数量：AI 写真、AI 算命

筛选与搜索：

- 按昵称搜索
- 按 App ID 搜索
- 按“生成过高考报告”筛选
- 按“已用完机会”筛选
- 按“无限生成用户”筛选

排序：

- 默认按最后进入时间倒序
- 可切换按最近报告时间倒序

### 4.4 用户详情

点击用户进入详情页或抽屉，展示：

- 基础身份：昵称、App ID、内部 user_id、头像、状态、创建时间、最后进入时间。
- 高考生成状态：总报告数、未删除报告数、已删除报告数、是否还能生成、是否无限生成。
- 报告记录：标题、生成时间、删除时间、查看入口、分享入口。
- 其他模块记录：AI 写真任务数、AI 算命任务数。
- 管理操作区：重置机会、开启无限、取消无限。

### 4.5 重置生成机会

管理员点击“重置生成机会”后，用户可以重新生成高考志愿报告。

重要原则：

- 不删除旧报告。
- 不清空旧报告。
- 不改旧报告的 `deleted_at`。
- 只新增一条“生成权限重置”的记录。
- 用户历史仍可追溯。

推荐逻辑：

```text
普通用户默认规则：
未删除报告数为 0，并且历史报告数小于 2，才可生成。

重置后规则：
只统计 reset_at 之后生成的报告数量。
reset_at 之前的旧报告仍保留，但不再占用本轮生成机会。
```

这样比直接删数据更稳，也方便以后解释“为什么这个人能重新生成”。

### 4.6 无限生成

管理员可以给指定用户开启“无限生成”。

适用对象：

- 内部测试人员
- 运营演示账号
- 客服排查账号
- 临时体验账号

无限生成用户：

- 不受高考报告次数限制。
- 仍然保留报告记录。
- 仍然受基础接口限流保护，避免误点或脚本刷爆。
- 页面上可以显示“内部测试账号”提示。

管理员也必须能取消无限生成。

### 4.7 操作审计

每次管理动作必须写日志：

- 操作人 App ID
- 操作人昵称
- 被操作用户 App ID
- 动作类型
- 操作前状态
- 操作后状态
- 操作时间
- 备注

动作类型建议：

- `reset_generation_limit`
- `enable_unlimited_generation`
- `disable_unlimited_generation`
- `view_user_detail`

第一版可以只对写操作记审计；查看详情是否记日志可后置。

## 5. 安全红线

管理员功能是写权限，不能只靠前端显示按钮保护。

### 5.1 当前风险

当前生产环境里 `APP_AUTH_VERIFY_URL` 为空，历史兼容逻辑允许 App WebView 通过裸 `app_user_id` 建立会话。这个逻辑对普通体验还能容忍，但对管理员写操作不够安全。

风险是：如果有人构造请求冒充 `734275` 或 `10`，可能绕过管理员判断。

### 5.2 第一版必须做的保护

至少满足以下之一：

方案 A，推荐：

- 接入真实 App token 校验。
- 生产环境不再接受裸 `uid` / `app_user_id` 创建管理员会话。
- 管理员接口只信任服务端校验后的 App 身份。

方案 B，临时可用：

- 管理入口可按 App ID 显示。
- 进入管理台或执行写操作前，要求输入一个服务端配置的管理员二次口令。
- 二次口令只存在服务器环境变量里，例如 `GAOKAO_ADMIN_ACTION_PASSWORD`。
- 二次验证通过后写入短期管理员会话，例如 2 小时。

如果短期内 App token 校验还没准备好，先走方案 B。安全措施不能省。

### 5.3 接口保护

所有管理员接口必须服务端校验：

- 当前请求有合法用户 session。
- 当前用户 App ID 在管理员名单里。
- 如果未接入 App token 校验，则必须有二次管理员会话。
- 写操作必须写审计日志。

普通用户直接请求管理接口，应返回 403。

## 6. 数据设计

### 6.1 管理员名单

第一版最省事的方式：

```env
GAOKAO_ADMIN_APP_USER_IDS=734275,10
```

但更推荐落数据库，方便后续管理：

```text
gaokao_app_admins
- id
- app_user_id
- role: owner/admin/viewer
- status: active/disabled
- created_by_app_user_id
- created_at
- updated_at
```

第一版可以先用环境变量启动，第二版迁到表。不要同时做太多。

### 6.2 用户生成权限覆盖表

推荐新增：

```text
gaokao_user_generation_overrides
- id
- user_id
- is_unlimited
- reset_at
- note
- updated_by_app_user_id
- created_at
- updated_at
```

解释：

- `is_unlimited=true`：该用户无限生成。
- `reset_at`：生成次数从这个时间之后重新计算。
- `note`：管理员备注，比如“客服帮用户重置一次”。

### 6.3 审计日志

可以复用现有 `admin_audit_logs`，但因为现有表偏传统后台账号，建议 metadata 写清楚 App 管理员信息：

```json
{
  "adminAppUserId": "734275",
  "adminNickname": "离心之巅",
  "targetAppUserId": "539612",
  "before": {},
  "after": {},
  "note": "用户资料填错，允许重新生成一次"
}
```

如果后续 App 管理台越来越重，再新增专用表：

```text
gaokao_admin_action_logs
```

第一版不必急着新建两套日志。

## 7. 服务端逻辑调整

当前生成权限核心在 `getGaokaoGenerationStatus(userId)`。

第一版要改成：

```text
1. 查用户 app_user_id。
2. 查 generation override。
3. 判断是否无限生成。
4. 如果有 reset_at，只统计 reset_at 之后的报告。
5. 返回 canGenerate、isUnlimitedTestUser、totalReports、activeReports、deletedReports、message。
```

注意：

- 用户列表里的“总报告数”可以展示真实全部报告数。
- 生成权限判断里的“计数”可以展示“本轮计数”，避免用户困惑。
- 文案要说明“管理员已重置生成机会”。

## 8. API 设计

建议新增接口：

```text
GET  /api/gaokao/admin/me
GET  /api/gaokao/admin/users
GET  /api/gaokao/admin/users/:userId
POST /api/gaokao/admin/users/:userId/reset-generation
POST /api/gaokao/admin/users/:userId/enable-unlimited
POST /api/gaokao/admin/users/:userId/disable-unlimited
GET  /api/gaokao/admin/audit-logs
```

如果走二次口令：

```text
POST /api/gaokao/admin/verify
POST /api/gaokao/admin/logout
```

接口返回尽量只给管理所需字段，不返回敏感图片原图、临时上传图、密钥或完整请求头。

## 9. 前端页面设计

### 9.1 志愿助手主页面

管理员进入 `/ai/gaokao`：

- 显示 `管理` 按钮。
- 显示位置靠近用户头像和昵称。
- 不影响生成报告主流程。

普通用户：

- 不显示管理按钮。
- 不暴露管理接口路径。

### 9.2 管理台页面结构

```text
顶部：高考助手管理台 / 当前管理员昵称 / 返回志愿助手

概览卡：
- 使用用户
- 生成报告
- 今日进入
- 无限生成用户

标签：
- 用户
- 报告
- 权限
- 操作记录
```

第一版可以只做“用户”标签，其他用入口占位都不需要。少做一点，先可用。

### 9.3 用户列表交互

每行用户右侧放操作：

- 查看
- 重置
- 开无限 / 取消无限

重置和开关无限都必须二次确认：

```text
确认给「泡泡呀」重置生成机会？
旧报告不会删除，只是允许重新生成。
```

### 9.4 用户详情交互

详情页重点让管理员快速判断：

- 这个人是否用过高考助手。
- 为什么他现在不能生成。
- 是否已经删除过报告。
- 是否需要重置。

建议显示一行判断文案：

```text
当前状态：已生成 2 次且全部删除，普通规则下已用完机会。可重置一次。
```

## 10. 可以新增的运营功能

### 10.1 第一版后可加

- 报告搜索：按标题、昵称、App ID 搜索。
- 报告查看：管理员可只读打开用户报告。
- 分享链接复制：方便客服转发或核查。
- 异常报告标记：报告为空、推荐数太少、标题异常时高亮。
- 用户备注：给用户加内部备注，如“客服已处理”。

### 10.2 运营看板

- 今日进入人数
- 今日生成报告人数
- 今日分享人数
- 报告删除人数
- 用完机会人数
- 重置次数
- 无限生成账号数

如果没有独立访问日志，先只做数据库里能准确统计的指标，不要硬造数据。

### 10.3 质量巡检

自动标记：

- 推荐结果为空
- 冲稳保数量明显不足
- 报告标题缺少姓名
- 报告 summary 过短
- 用户生成失败

这些能帮助运营快速发现“用户说不好用”的根因。

### 10.4 客服辅助

后台根据用户状态生成一句客服话术：

```text
你当前已经生成过 2 次报告，普通规则下机会已用完。我们已为你重置一次，可以重新进入生成。
```

这比让客服自己判断更稳。

### 10.5 数据健康检查

显示：

- 四川投档数据条数
- 2026 招生计划条数
- 一分一段表条数
- 最近一次导入时间
- 当前推荐是否可用

这个适合后续放到“系统状态”页。

## 12. 开发红线

- 不要删除用户历史报告。
- 不要用“删除旧报告”来实现重置。
- 不要把管理员名单写死到前端。
- 不要只靠按钮隐藏保护管理接口。
- 不要在未解决身份安全前开放无保护写接口。
- 不要影响 AI 写真、AI 算命现有生成记录和额度。
- 不要把本地库数据当成生产数据。
- 不要把 `.env.local` 打进部署包。

## 13. 测试清单

### 13.1 权限测试

- 普通用户没有管理按钮。
- 普通用户访问 `/ai/gaokao/admin` 被拒绝。
- 普通用户请求管理 API 返回 403。
- 离心之巅可进入管理台。
- 练团长可进入管理台。
- 管理员二次验证失败时不能执行写操作。

- 确认旧报告仍在。

- 用户重新生成后，报告新增。

### 13.3 无限生成测试

- 给测试用户开启无限生成。
- 用户有未删除报告时仍可重新填写并生成。
- 取消无限后恢复普通规则。
- 审计日志记录开启和取消。

### 13.4 数据列表测试

- 用户列表包含离心之巅、练团长、泡泡呀等真实用户。
- 报告数和数据库一致。
- 删除数和未删除数一致。
- 搜索 App ID 能定位用户。

### 13.5 回归测试

- `/ai/gaokao` 普通生成流程不变。
- `/ai/photo` 可打开。
- `/ai/fortune` 可打开。
- AI 写真和算命历史不受影响。

## 15. 推荐第一版任务拆分

建议按这个顺序做：

1. 先补管理员身份保护，确定用 App token 校验还是二次管理员口令。
2. 新增生成权限覆盖表和审计日志写入。
